# LEDs

How the plugin drives the LEDs of DX, DXP and iDX models. Off until the user switches them on in the plugin.

## LED controller

All DX, DXP and iDX models share the same LED controller protocol, after [miskcoo/ugreen_leds_controller](https://github.com/miskcoo/ugreen_leds_controller) (credits: [third-party.md](third-party.md)). Bays map to LEDs by SATA port.

- The LED part is offered when the DMI product name starts with `DX`, `DXP` or `iDX`, and not while the plugin _ugreenleds-driver_ or the kernel module `led_ugreen` holds the controller.
- Transport: SMBus (`/dev/i2c-N`), or `/dev/mem` on the DXP4800 GT (AMD DesignWare I2C) and, by default when every check passes, on DXP2800 SUB2 boards (Intel LPSS DesignWare I2C). Protocol and frames: `backend/internal/led/chip/protocol.go`.
- DXP480T Plus: no controller at 0x3a, only a power LED on a simpler chip (0x26) that flashes white until it gets the steady-white init (`ugreen-led-ctl dxp480t`, includes a short orange flash as in ich777's driver). `ugreen-nas-ctl led-*` boot sends it once instead of probing, only while LED control is on; with it off the LED stays untouched, as on every model. The model has 0 bays.
- Frames (`chip/frames.go`): DX/DXP models take the 12-byte I2C block write with the LED ID first; the iDX models and the DXP4800 GT an SMBus block without the ID. The DXP2800 (exact name only) picks the first frame by the DMI system version (`/sys/class/dmi/id/product_version`): `EM_` in it, or an unreadable or placeholder version, means the DX/DXP frame first, any other version (for example `DXP2800 V1.2 251215`) the iDX frame first, the rule of [miskcoo's README](https://github.com/miskcoo/ugreen_leds_controller#readme) after commit f0fcd81. Either way, when the controller does not acknowledge the first frame (register 0x80) the other one follows, which is the one UGREEN's own driver uses for that model (V1.2 board, [miskcoo#128](https://github.com/miskcoo/ugreen_leds_controller/issues/128)). An owner confirmed the LEDs of a V1.2 board with that SMBus block frame using miskcoo's tool (his README marks V1.2 experimental). The frame that worked last is tried first for the rest of the process. `UGREEN_LAYOUT=idx` forces the iDX frame by hand.
- Controller that rejects everything: the address answers a detect (one-byte read) but every read and write NAKs, as on a DXP2800 with BIOS `EM_DXP2800_SUB2_V1.0.27` ([miskcoo#133](https://github.com/miskcoo/ugreen_leds_controller/issues/133)). `ugreen-led-i2c` then exits with 4 and one message (`rejects every read and write`), after one pass over both frames and without trying the other LEDs; `ugreen-led-ctl status` reports `i2c_probe: "rejected"` plus `i2c_error`; the status daemon logs the message once, writes nothing and probes again after 30 s, doubling up to 10 min, and starts over when the controller answers.
- Stop: the status daemon ends every activity blink (bays and network LED) on SIGTERM, so none stays in a blink. `ugreen-led-ctl daemon stop` (also run by plugin removal and `ugreen-nas-ctl led-stop`) then applies the saved settings to all LEDs including `netdev`; LEDs without saved settings keep their last status look, steady.
- Network LED: the daemon probes every 30 s. The link is checked first and counts at once: operstate not `up`, or carrier 0 on the device and on all its bond or bridge members, is red. Then the kernel neighbour table is read for the gateway of the first default route (lowest metric, not the `shim-` route Unraid adds for Docker; the same route that picks the LED device, a bridge such as `br0` resolving to its uplink port): `ip -j neigh show <gateway> dev <dev>` (IPv4 or IPv6), or `/proc/net/arp` for IPv4 when `ip -j` gives no JSON. No packet is sent, so a router that ignores pings keeps the LED green. An entry in state REACHABLE, STALE, DELAY, PROBE, PERMANENT or NOARP is fine (a STALE entry on an idle box is normal, the kernel ages entries without traffic); FAILED, INCOMPLETE or no entry is a miss. Three misses in a row (about 90 s) turn the LED red, one live entry resets the count, and a lost link resets it too. A gateway that vanished shows up once traffic to it fails and the kernel marks the entry FAILED: the LED means "network reachable", not "internet reachable". `ugreen-led-ctl status` and `ugreen-nas-ctl diag` show `network_ok` true with `network_reason` `ok (gateway neighbour STALE)` (the state, never the address or MAC), or `ok (gateway neighbour FAILED, 1 of 3)` while it counts; red reads `gateway neighbour FAILED` or `no neighbour entry for the gateway`. `ugreen-led-ctl apply` (the settings reload) does not touch the count; restarting the daemon starts it at 0 and probes once at start.
- Standby: a bay follows `spundown` of `disks.ini` every 5 s and is written only when its look changes, so a SMART read of a sleeping disk writes nothing and a wake or sleep rewrites it once.
- Timing: blink on and off at least 100 ms; breath on at least 1000 ms, off at least 500 ms (the limits UGREEN's drivers apply). Shorter values are raised.
- iDX6011 Pro: DMI name exactly `iDX6011 Pro` (UGREEN lists no other Pro; any other name with "Pro" gets no iDX layout). The second LAN LED is register 2, name `netdev2` in `ugreen-led-i2c` (also part of `all`); `ugreen-led-ctl` accepts it on that product only (`list`, `all`, per-LED commands; the help text stays model-independent); the plugin pages do not offer it.
- DXP2800, DXP6800, DXP6800S (exact DMI names): the DX/DXP frame first, the iDX frame as fallback, as UGREEN's driver serves the three together (`leds-mcu.c:171-173,558-561@c75c5ab`; 4 LEDs on the DXP2800, 8 on the other two). `DXP6800 Pro` and `Plus` stay on the DX/DXP frame.
- DXP2800 GT: no I2C controller, see below.
- Facts from UGREEN's GPL kernel drivers are cited as `file:line@c75c5ab` in the code and in [third-party.md](third-party.md); nothing is copied.
- If the standalone UGREEN LED Control plugin is installed too, both write the same LEDs and the last write wins ([conflicts.md](conflicts.md)).

## DXP2800 GT (CS201x)

No I2C controller: four ARGB channels (power, network, disk1, disk2) sit in the Chipsea CS201x embedded controller, reached through the host-to-EC window the fan driver uses (`backend/internal/hw/cs201x`). Registers after `ug_201x.c:102-120,375-407@c75c5ab`, channels after `leds-sio-201x.c:93-98`. UGREEN's LED driver is not in its Makefile and marks every write call TODO. Other tools control all four channels on a device after the same boot-finish write of 1 to `ARGB_FLOW_CONTROL` ([miskcoo#123](https://github.com/miskcoo/ugreen_leds_controller/issues/123); a user reports a month on TrueNAS); nobody has run this plugin's path yet.

- Off by default. The backend answers only with `cs201x_leds="1"` in `leds.cfg` (the key is not in the web UI); without it every `ugreen-led-i2c` command except the dump fails with a hint. It also refuses while a UGREEN kernel module (`leds_sio_201x`, `ug_201x`, `ug_sio201`) is loaded.
- Read only: `ugreen-led-i2c cs201x` (or `ugreen-led-ctl cs201x`) prints chip id, host interface, base address, flow control and per channel mode, brightness, colour, period and duty. It never switches the host interface on and needs no opt-in.
- Writes: colour (B, R, G bytes), brightness, mode (0 off, 1 on, 2 blink, 3 breath). Blink and breath store the cycle and the on part in 50 ms units (period, duty; at most 255 units = 12.75 s), the mode last. A write switches the host interface on if it is off (`cfg 0x30 = 1`, as UGREEN does on load) and sets `ARGB_FLOW_CONTROL` (0x20005440) to 1. No effects (rainbow, temperature).
- Snapshot: before its first write the backend saves flow control and all four channels to `/var/run/ugreen-nas-control.led.cs201x` (an existing file is kept); `ugreen-led-i2c cs201x restore` writes it back and deletes it. `ugreen-led-ctl daemon stop`, a SIGTERM of the daemon and a yield to another LED tool restore it; the saved manual settings are not applied afterwards on this model.
- Locking: every register access runs under the flock `/var/run/ugreen-nas-control.lock`, the one the fan tool and daemon use per operation, so the fan driver and the LED backend (separate processes) never interleave an address latch. The lock is never nested.
- Other LED tools: the status daemon's rival detection applies as on every model (it exits and restores).

## DXP2800 SUB2 (Intel LPSS I2C)

BIOS `EM_DXP2800S_SUB2_*`: the LED MCU (ACPI `HT32F522`, `\_SB_.PC00.I2C1.MCU0`) is not on the I801 SMBus but behind an Intel Alder Lake-N LPSS DesignWare I2C controller (PCI 00:15.0/.1, 00:19.0/.1) that has no I2C driver (nothing, or only `intel-lpss` bound, see below), and Unraid's kernel 6.18.58 ships no `i2c_designware` module ([#214](https://github.com/ugreen-nas-control/ugreen-nas-control/issues/214), [miskcoo#115](https://github.com/miskcoo/ugreen_leds_controller/issues/115)). The plugin drives the controller through `/dev/mem`, like the AMD one on the DXP4800 GT (`backend/internal/led/chip/lpss_linux.go`, shared transfer code in `dwmem_linux.go`). Confirmed on a SUB2 board (`EM_DXP2800S_SUB2_V1.0.11`, PCI 00:15.1, `lpss_leds="1"`, 5.5.0-next.000133, [#214](https://github.com/ugreen-nas-control/ugreen-nas-control/issues/214)): after a full cold reboot the LEDs came back by themselves as configured, the LED and fan daemons started without help and dmesg showed no LED or I2C errors; `led-enable` starts the daemon without errors, Identify lights network (LED 1), disk1 (LED 2), disk2 (LED 3) and the power button in bay order, colours and activity blink work, `diag` reports `led_controller ok (bus /dev/mem#lpss)`, disk3 and disk4 stay off.

- On by default, no key needed. `lpss_leds="0"` in `leds.cfg` (not in the web UI) is the opt-out: the path is never used; `lpss_leds="1"` is accepted and means the default. The path is picked only when all gates hold: the I801 SMBus answers NAK at 0x3a (ENXIO or EREMOTEIO) or there is no I801; an ACPI device `HT32*` whose parent controller maps to exactly one Intel class 0c80 PCI function; that function has no driver, or `intel-lpss` with no `i2c_designware` child driver and no I2C adapter; every read check below passes; the chip id read returns 0xC5B2 before any LED frame. Boxes without an HT32 device (other models, DXP4800 GT) never reach it. On any refusal the plugin behaves as without this path (no controller found on the normal buses): the first refusal of a boot is kept in `/var/run/ugreen-nas-control.lpss-state` (`refused: <reason>`, shown by `ugreen-nas-ctl diag`), and later commands skip the path without touching `power/control`, PCI or `/dev/mem` until the next boot. A controller that answered once in the boot (`ok`) is not switched off by a later failure.
- Test: `ugreen-led-i2c lpss-probe` is read only: it prints the discovery and read checks and stops before any write or writable mapping, ending with a `next:` line. `ugreen-led-i2c lpss-probe --write` runs the bring-up and the chip id read below; it needs no opt-in. Both exit 1 on the first refusal. `ugreen-nas-ctl diag` shows its last result (kept in `/var/run/ugreen-nas-control.lpss-probe`), the state file above and, without a run, only the static ACPI and PCI facts; diag never brings the controller up.
- Read only first: the ACPI device with a `HT32*` hid, its path minus the last segment, the PCI function whose `firmware_node/path` equals it (exactly one), vendor 8086 and class 0c80, no driver bound (or only `intel-lpss` with no I2C driver below it, next bullets), memory decoding on and power state D0 (config space PMCSR, never written), BAR0 from sysfs `resource`, then a read-only mapping of BAR0 for the DesignWare component type `0x44570140` (`0xFC`).
- `intel-lpss` bound, no I2C driver: Unraid ships `intel-lpss-pci.ko` but no `i2c_designware`, so the MFD parent can own the PCI function while nothing drives the I2C controller below it (#214: 00:15.0/.1 and 00:19.0/.1 report driver `intel-lpss`, no adapters). That one state is accepted, only when all hold: the driver name is exactly `intel-lpss` (`intel-lpss-pci.c:654`); the MFD child `i2c_designware.N` (`mfd_add_devices`, `intel-lpss.c:448`) has no `driver` link (`idma64.N`, `:441`, may be bound: its own register window at +0x800, size 0x800, `intel-lpss.c:46-47,102-114`, is never touched; the probe prints `lpss.idma64`); no `i2c-N` adapter exists below the function nor as a `/sys/class/i2c-adapter` or `i2c-dev` device whose parent chain leads to it. Any other driver, a child with a driver or an adapter is refused and the report names the rule (`other-driver`, `child-driver`, `adapter`). The read only probe adds `lpss.children`, `lpss.adapters`, `pm.control`, `pm.runtime_status` and the `RESETS` value (intel-lpss writes it at probe and resume, `intel_lpss_deassert_reset`, `intel-lpss.c:259-265`).
- Runtime PM of the bound function: `intel-lpss-pci.c:83-84` ends the probe with `pm_runtime_put` and `pm_runtime_allow`, so `power/control` is `auto` and the idle function suspends; the runtime suspend writes `RESETS` 0 (`intel-lpss.c:514`, `RUNTIME_PM_OPS` `:536`); a suspended function answers register reads with 0xFF. The read only probe never wakes it: with `runtime_status` other than `active` it prints the two PM lines and stops, because even reading the sysfs `config` file resumes the function (`drivers/pci/pci-sysfs.c:763`). `lpss-probe --write` and LED control first save `power/control`, write `on` (a kernel sysfs interface, not a register: `Documentation/ABI/testing/sysfs-devices-power:35-50`, `Documentation/power/runtime_pm.rst:633-640`; it wakes a suspended device) and wait up to 1 s for `runtime_status` `active`, else refuse. Then the checks and writes below follow, and the `RESETS` write is skipped when it already shows the reset released (the runtime resume callback releases it, `intel-lpss.c:524`). Nothing else of the LPSS (clock, other private registers) is touched. On every exit (success, refusal, failure, timeout) the controller is disabled as before and the saved `power/control` value is written back. The saved value is kept in `/var/run/ugreen-nas-control.lpss-power` while it is `on`; a run that finds the file (earlier crash) restores that value, not the leftover `on`. One opened handle (one `ugreen-led-i2c` command, one `lpss-probe --write`, one LED daemon call) writes `on` once and holds it over every transfer of that handle, so `power/control` is `on` only while a command runs and the function runtime suspends (RESETS 0, DesignWare registers back to reset values) between two commands. The resume callback only deasserts RESETS and restores the LPSS private registers (`intel_lpss_resume`, `intel-lpss.c:519-532`), so each open runs the whole bring-up again. Before every transfer the handle checks `runtime_status`, the component type, RESETS, `SS_SCL_HCNT/LCNT` and `IC_CON`; when one is off it writes `on` again and repeats the bring-up. A chip id of 0x0000 is never taken for a different chip: the bring-up is repeated once, a second 0x0000 ends with "chip id 0x0000 twice" and the advice to send a trace. `ugreen-led-i2c --debug <command>` (or `UNC_LPSS_DEBUG=1`) prints every step (power, `runtime_status`, bring-up, each transfer with its bytes and result) with a time stamp to stderr.
- `get all` lists every LED name whose status the chip answers, on every model; it does not cut the list to the bays (UGREEN's driver counts 4 LEDs on the DXP2800 and 8 on the DXP6800, `leds-mcu.c:62-63,558-561@c75c5ab`). A SUB2 board answered for disk1 to disk4, netdev and power (#214), all with the same values (mode on, brightness 180, white, 256/512 ms), which looks like the chip's register defaults for slots the board has no LED on: only power, netdev, disk1 and disk2 are real.
- Runtime PM: PCI runtime power management could in theory change the power state between the D0 check and the writes; the probe reads `COMP_TYPE` again on the writable mapping right before the first write and refuses on a mismatch.
- Then, with `lpss-probe --write` or LED control, writes: (1) `RESETS` at BAR0+0x204 = 0x7 (function 0x3, iDMA 0x4), only when it reads otherwise; (2) `IC_ENABLE` 0, `SS_SCL_HCNT` 552, `SS_SCL_LCNT` 652, `SDA_HOLD` 0x10006, `TX_TL`, `RX_TL`, `IC_CON` (master, standard mode 100 kHz); (3) `IC_TAR` 0x3a, `IC_ENABLE` 1, and the transfer: write 0x5A, restart, read two bytes. No LED frame is sent unless the word is 0xC5B2; on a mismatch, a NAK or a timeout `IC_ENABLE` is set to 0 again.
- Facts. Vendor: address 0x3a, chip id register 0x5A read as a word, expected 0xC5B2 (`leds-mcu.c:41,59,716-717,761-791@c75c5ab`), frames `leds-mcu.c:200-219@c75c5ab` (already in `protocol.go`). Linux 6.18: LPSS private registers at BAR0+0x200 (`drivers/mfd/intel-lpss.c:43`), `RESETS` at +0x04 with function 0x3 and iDMA 0x4 (`intel-lpss.c:50-52`) and the 0x7 write (`intel_lpss_deassert_reset`, `intel-lpss.c:259-265`; `intel_lpss_init_dev` writes 0 first, `:267-274`); PCI IDs 54c5, 54c6, 54e8, 54e9 are `bxt_i2c_info` (`intel-lpss-pci.c:416-420`) with a 133 MHz input clock (`:173-176`) and SDA hold 42 ns, SDA fall 171 ns, SCL fall 208 ns (`:162-166`); the clock divider is registered for non-I2C devices only, so the I2C clock register is never touched (`intel-lpss.c:358`); standard mode counts `HCNT = round(133000 kHz x (4000 + 171) ns / 1e6) - 3`, `LCNT = round(133000 x (4700 + 208) / 1e6) - 1` (`i2c-designware-master.c:66-83`, `i2c-designware-common.c:417-458`); SDA hold from nanoseconds (`i2c-designware-platdrv.c:281-283`) plus RX hold 1 (`i2c-designware-common.c:488-491`).
- Refusals (nothing written): no `HT32*` ACPI device; ACPI path without a parent; not exactly one PCI function with that firmware node; vendor not 8086 or class not 0c80; a driver other than `intel-lpss` bound, an `i2c_designware.N` child with a driver or an I2C adapter below it, `power/control` or `runtime_status` unreadable, `power/control` neither `auto` nor `on`, no `active` within 1 s after `on`; config space unreadable; memory decoding off; no power management capability; not D0 (the plugin does not write PMCSR); BAR0 not a memory region of 4 KiB; BAR0 not mappable; component type different on the writable mapping; component type not `0x44570140` (the report says when `RESETS` shows the controller in reset). After the write phase starts: component type wrong after the reset write, controller setup failure, NAK or timeout on 0x3a, chip id not 0xC5B2.

## LED tool and backend

- `ugreen-led-i2c` (`backend/internal/led/chip`): writes colour, brightness and effects to the controller.
- `ugreen-led-ctl` (`backend/internal/led/ledctl`): decides what each LED shows (status mode from `disks.ini`, SMART and link speed, night mode, alerts, shutdown signal, effects) and calls the LED tool. Its runtime state is `/var/run/ugreen-nas-control.led*`, its settings `leds.cfg`. The behaviour it must keep is [SPEC.md](../backend/internal/led/ledctl/SPEC.md).
- `web/plugin/led/api.php` runs `ugreen-led-ctl` per request.
- `ugreen-nas-ctl led-*` switches the LED part on and off and imports the settings of UGREEN LED Control ([cli.md](cli.md)).
- Shutdown: the Unraid event script `plugin/event/stopping` runs `ugreen-nas-ctl event stopping`, which tells the LED backend so the power LED can signal it.
